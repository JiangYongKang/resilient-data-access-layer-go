# 迁移协议与结构兼容规则

本文档说明 `internal/migrate` 的版本化迁移协议、幂等与回滚保证、破坏性变更
策略，以及读取方在结构演进下的兼容规则。

## 1. 基本模型

- 每个版本是一个 `Migration{Version, Name, Destructive, Up}`，`Up(tx)` 在
  **版本事务**内完成该版本的全部结构变更与必要回填。
- 登记表 `schema_migrations(schema_version, name, checksum, applied_at)` 记录
  已应用版本；审计表 `schema_destructive_approvals(schema_version, scope)` 记录
  已授权的破坏性变更。两张表在首次迁移时由独立事务幂等创建。
- `Runner.Migrate(ms, targetVersion)` 按版本升序执行；`targetVersion<=0` 表示
  迁移到最新。

## 2. 静态前置校验（在任何脚本执行之前）

满足任意一条即整体拒绝，不执行任何脚本：

1. 版本号必须为正整数；
2. 版本号在一次迁移集内**严格递增且不重复**，否则 `MIGRATION_BAD_ORDERING`；
3. `Up` 不得为 nil；
4. 已应用版本的身份（版本+名称+破坏性标记）算出的校验和必须与登记一致，
   否则 `MIGRATION_CHECKSUM_CHANGED`；
5. 不允许在“当前版本”之后补应用更旧的版本。

> 校验和是版本的**身份指纹**（版本号、名称、破坏性标记），不包含函数指针等
> 不稳定值。脚本内部逻辑的正确性由代码评审、审计表与回滚测试共同保证。

## 3. 幂等语义（可重复执行）

对同一份迁移集反复调用 `Migrate`：

- 已应用版本进入 `Summary.Skipped`，**不重新执行脚本**，也不写任何数据；
- 脚本本身仍被要求写成幂等（先 `HasTable` / 查列是否存在再操作），这样即使在
  登记之外被人工触发也安全；
- 幂等的判定依据可在日志中断言：第一次 `Applied=[1 2 3]`，之后恒为
  `Applied=[] Skipped=[1 2 3]`，业务表行数不变。

## 4. 失败整批回滚（不留半套结构）

每个待应用版本独立开启一个事务：

```
begin
  (Destructive=true 时) 授权破坏性 DDL + 写审计
  Up(tx)                      # 建表/加列/回填
  insert schema_migrations    # 登记本版本
commit
```

- `Up` 返回任何错误（包括脚本内人为失败、类型/约束错误、未授权破坏性 DDL）：
  事务回滚，**该版本已完成的建表、加列、回填一并撤销**，登记表不写该版本，
  后续版本不再执行；
- 错误以 `MIGRATION_FAILED`（破坏性越权为 `DESTRUCTIVE_CHANGE_DENIED`）返回，
  并 `Unwrap` 到根因；
- 之前已应用的版本完全不受影响，数据库停留在“上一个已提交版本”的一致状态。

修复脚本后重新执行 `Migrate` 即可从失败版本重试（登记中没有该版本）。

## 5. 新增列的默认值规则

`AddColumn` 的默认语义是确定且稳定的：

1. 列必须声明 `HasDefault+Default`，或 `Nullable:true`（默认 nil）；
   不允许新增“NOT NULL 且无默认值”的列，否则迁移在该版本事务内失败回滚；
2. 既有行在加列时立即获得该默认值（行本身不被视作“修改”，行版本不变）；
3. 加列之后插入的新行，未提供该列时取**同一个**默认值；
4. 领域读取层对缺失列做防御式处理（取与迁移一致的默认值），但正常路径下
   不会出现缺列。

## 6. 删列与改名字段（破坏性变更）

- 默认**禁止** `DropColumn` / `RenameColumn`：引擎在事务级拒绝，版本事务回滚，
  返回 `DESTRUCTIVE_CHANGE_DENIED`；
- 只有显式 `Destructive: true` 的版本，迁移器才会对该事务 `AllowDestructive()`
  并在审计表登记授权（随版本事务提交/回滚）；
- 推荐的兼容演进方式（避免删列/改名）：
  - 要“删”一个字段：先让写入方停止写、读取方忽略该列，保留列做影子列，必要时
    再在一个明确声明的破坏性版本里删除；
  - 要“改名”一个字段：新增一列（新名，带默认值）→ 双写/回填 → 读取方切到新列
    → 旧列进入影子期 → 最后才在破坏性版本里删旧列。

## 7. 读取方为什么不会“静默错位”

- 存储层 `List/Get` 以 `map[列名]值` 投影，并始终附带隐式 `id`、`version`；
- 领域映射（如 `account.mapRow`）一律**按列名取值**，与列的物理顺序无关：
  新增列插入到任意位置都不会把旧数据错位到别的字段；
- 读取到的标量类型按列声明严格断言，类型不符直接报错，而不是吞掉或乱填。

## 8. 本地验证清单

```bash
go test ./internal/migrate/ -race -v
```

覆盖：失败版本整批回滚（失败版本的建表/加列均不存在、登记停在上一版本）、
重复执行幂等（行数与登记不变）、校验和漂移拒绝、未声明破坏性变更拒绝与声明后
审计落库、版本重复/乱序拒绝。日志中每条用例都打印“输入”和“判定依据”。
